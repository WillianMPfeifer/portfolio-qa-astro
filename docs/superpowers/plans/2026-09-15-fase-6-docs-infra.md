# Fase 6 — Docs (infraestrutura) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the `/docs` infrastructure (thematic sidebar, a working language switcher, visually-matching tokens) so the section is ready for the author to add real technical content at his own pace — no content is written in this phase.

**Architecture:** Starlight's own `Header` component stays untouched (keeps Search/Pagefind, social icons, theme select working) and gets re-themed purely via CSS custom-property overrides loaded through `customCss`. Only `LanguageSelect` is swapped for a real custom component, because that one has a functional bug (wrong link), not a cosmetic one. Sidebar categorization uses Starlight's `autogenerate` per directory, confirmed (by reading the installed package's source, not assumed) to resolve the correct locale-specific directory on its own.

**Tech Stack:** Astro 7.3.2, `@astrojs/starlight` 0.42.0 (no new dependencies).

## Global Constraints

- No real documentation content is written in this phase — every task must work correctly against the existing placeholder-only `/docs` (just `index.md` in each locale).
- Sidebar categories: exactly `web`, `mobile`, `processo` (autogenerated directories) — these mirror the two published case studies (Cypress, Appium) plus a process/QA-management category.
- Portuguese content always lives under a single `pt/` at the root of `docs/docs/` (never a `pt/` folder per category) — `docs/docs/pt/web/<slug>.md`, not `docs/docs/web/pt/<slug>.md`.
- Do not replace Starlight's `Header` component — only override CSS custom properties and, separately, `LanguageSelect`.
- CSS overrides for Starlight's `--sl-color-*` variables must be unlayered (no `@layer` wrapper) — Starlight's own color rules live inside `@layer starlight.base`, and CSS gives unlayered author styles priority over any layered rule regardless of selector specificity. Confirmed by reading `node_modules/@astrojs/starlight/dist/integrations/vite-virtual-modules.js` (the `virtual:starlight/user-css` module is a flat sequence of plain `import` statements, not wrapped in any layer).
- A single unconditional `:root { --sl-color-bg: var(--paper); ... }` block is sufficient for both light and dark mode — do not write a separate `:root[data-theme='light']` block. `var(--paper)` (and the other site tokens) already resolve to the correct light/dark value on their own, because `src/styles/tokens.css` defines both the light default (bare `:root`) and the dark override (`:root[data-theme='dark']`) for the *same* custom properties elsewhere; referencing `var(--paper)` picks up whichever is currently in effect without needing to duplicate the conditional here.
- The `/docs` link added to `Header.astro` must NOT use `getRelativeLocaleUrl` — that helper assumes the standard `/pt/<path>` prefix pattern, but `/docs`'s Portuguese version lives at `/docs/pt/` (the deliberate nesting trick from spec §5.3), which diverges from that pattern. Use an explicit ternary instead (shown in Task 4).
- Commit messages end with `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`.

### Task 3: Custom `LanguageSelect`

**Files:**
- Create: `src/components/StarlightLanguageSelect.astro`
- Modify: `astro.config.mjs`

**Interfaces:** none — this component is self-contained (computes everything from `Astro.url.pathname`), nothing later depends on it.

- [ ] **Step 1: Write `src/components/StarlightLanguageSelect.astro`**

```astro
---
const pathname = Astro.url.pathname;
const isPortuguese = pathname === '/docs/pt' || pathname.startsWith('/docs/pt/');
const enHref = isPortuguese ? pathname.replace(/^\/docs\/pt/, '/docs') || '/docs/' : pathname;
const ptHref = isPortuguese ? pathname : pathname.replace(/^\/docs/, '/docs/pt') || '/docs/pt/';
const currentLocale = isPortuguese ? 'pt' : 'en';
---

<nav aria-label="Language">
  <a href={ptHref} aria-current={currentLocale === 'pt' ? 'page' : undefined}>pt</a>
  <span aria-hidden="true">·</span>
  <a href={enHref} aria-current={currentLocale === 'en' ? 'page' : undefined}>en</a>
</nav>

<style>
  nav[aria-label='Language'] {
    display: flex;
    align-items: center;
    gap: 0.4rem;
    font-family: var(--font-mono);
    font-size: 0.85rem;
  }

  nav[aria-label='Language'] a {
    color: var(--ink-soft);
    text-decoration: none;
  }

  nav[aria-label='Language'] a[aria-current='page'] {
    color: var(--ink);
    font-weight: 700;
  }
</style>
```

This is deliberately the same markup pattern (`nav[aria-label='Language']`, the `·` separator, `aria-current`) as `src/components/Header.astro`'s own language nav — same visual language, no `<select>` dropdown like Starlight's native one.

The path rewrite works because `/docs` is always mirrored 1:1 between locales (unlike `/projects/[slug]`, which needed `translationKey`/`resolveAltLocaleHref` in Fase 3 because case-study slugs deliberately diverge — there's no such divergence for docs).

### Task 4: Link `/docs` from the shared header

**Files:**
- Modify: `src/components/Header.astro`

**Interfaces:** none — this is the last content-touching task; Task 5 only verifies.

- [ ] **Step 1: Add the link**

Current relevant block (`src/components/Header.astro`):

```astro
  <div class="site-links">
    <a href={getRelativeLocaleUrl(currentLocale, '/')} class="site-name">Willian</a>
    <a href={getRelativeLocaleUrl(currentLocale, '/quality')}>quality</a>
  </div>
```

Change to:

```astro
  <div class="site-links">
    <a href={getRelativeLocaleUrl(currentLocale, '/')} class="site-name">Willian</a>
    <a href={getRelativeLocaleUrl(currentLocale, '/quality')}>quality</a>
    <a href={currentLocale === 'pt' ? '/docs/pt/' : '/docs/'}>docs</a>
  </div>
```

This does NOT use `getRelativeLocaleUrl(currentLocale, '/docs')` like the `/quality` link does, on purpose: that helper assumes the project's standard `/pt/<path>` prefix, but `/docs`'s Portuguese version is deliberately nested at `/docs/pt/` instead (spec §5.3's aninhamento trick) — `getRelativeLocaleUrl` would produce the wrong (orphan) URL here. The explicit ternary is the correct, simplest fix; don't "clean it up" back to `getRelativeLocaleUrl` later without re-reading this note.

No CSS change needed — `.site-links a:not(.site-name)` already styles every non-site-name link in this row, including this new one.

- [ ] **Step 2: Verify the crawler now discovers `/docs`**

Run: `npm run build && npm run test:e2e`
Expected: all 5 tests still pass. Then inspect `test-results/a11y-summary.json` — `routesChecked` should now be higher than the pre-existing count (10, as of the end of Fase 5) — the crawler starts at `/`, which now links to `/docs/` (via the header rendered on every page), and from there follows whatever `/docs/` itself links to (including the corrected pt/en switcher from Task 3, and the sidebar).

Do not hardcode an exact expected number here — the real count depends on exactly how many pages the crawler transitively reaches, which isn't worth predicting by hand. What matters: (a) the number went up from 10, confirming `/docs` pages are now actually being crawled, and (b) all 5 e2e tests still pass, meaning the a11y zero-tolerance gate found no violations on the newly-reached pages and no broken link turned up either.
